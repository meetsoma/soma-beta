# Migration v0.41.2 → v0.42.0

## Doctor Actions

```json
{
  "settings-defaults": {},
  "settings-subkeys": {
    "guard.trust": { "enabled": true, "threshold": 3, "ttlDays": 30 },
    "scripts.maxInPrompt": 40
  }
}
```

**The `guard.trust` default is deliberately NOT backfilled as-is for existing workspaces** —
see below. The boot sentinel `guard-trust-preserve-v0.42.0` writes `enabled:false` for any
workspace that predates this release.

## Summary

Two things in this release change behaviour for someone who upgrades rather than installs
fresh. Both are handled automatically; this doc records what and why.

### 1. `guard.trust` — earned command trust ships ON, but not for you

New in v0.42.0: approve the same normalised command in the same project `threshold` times
(default 3) and the guard stops asking, until `ttlDays` (default 30) of disuse expire the
entry. Ledger at `~/.soma/state/guard-trust.json`. It can only ever relax the *routinely
prompted* tier — `rm -rf`, force-push, `reset --hard`, `clean -f` and root-path truncation
are never relaxed by it.

For a **fresh install** that default is the intended product behaviour.

For an **existing workspace** it would be a guard-*relaxing* change applied silently on
upgrade — not what that user configured. So the boot sentinel
**`guard-trust-preserve-v0.42.0`** writes `guard.trust.enabled = false` into any workspace
whose recorded version is `< 0.42.0`, preserving always-ask. It never overwrites an explicit
choice (an existing `enabled` key is left alone), and fresh installs never match the gate, so
they keep `true`.

**To opt in after upgrading:**

```json
{ "guard": { "trust": { "enabled": true } } }
```

### 2. `body/children/_child.md` now resolves from the agent install

`compileChildPrompt` used to resolve the child-prompt template **only** from the body chain,
and nothing ever seeded it into a `.soma` — the seeding described in the v0.12→v0.20 phase
doc no longer exists in the code. The published tarball didn't carry the file either: the
package's `body/` is built by a non-recursive `cp templates/default/*.md`, while `_child.md`
lives in the repo's own `body/` tree.

Net effect before this release: **on a fresh npm install the chain resolved nothing and
`compileChildPrompt` threw** — `soma:agent.delegate` and `soma:agent.claude` could not run.
Dogfood never saw it, because a dogfood workspace carries its own copy.

Fixed in two places:

- **Packaging** — `soma-release.sh` now copies `body/children/_child.md` into the tarball and
  **hard-fails** if it is absent (a warn here is invisible until a user delegates).
- **Resolution** — after the body-chain walk, `compileChildPrompt` falls back to the agent
  install's own copy (`SOMA_CODING_AGENT_DIR` / `PI_CODING_AGENT_DIR` / `~/.soma/agent`).

**No workspace action required.** A workspace copy still wins if present — the override is
deliberate. Workspaces *without* one now track the shipped template and pick up slot changes
on upgrade instead of freezing a copy at install time.

Covered by `tests/test-child-template-resolution.sh` (hermetic `HOME`; falsified by
neutering the fallback — cases 1/1b go red).

### 3. `scripts.maxInPrompt` (default 40)

Caps how many scripts render in the boot `scripts_table`. Previously uncapped, so a
workspace with more than 40 scripts will render a shorter table than before. Cosmetic,
prompt-size-reducing; raise the key if you want the old behaviour.

## Actions

1. Boot sentinel `guard-trust-preserve-v0.42.0` runs automatically — writes
   `guard.trust.enabled=false` for workspaces recorded below `0.42.0`.
2. No action for `_child.md` — resolution now falls back to the agent install.
3. Set version to `0.42.0`.
